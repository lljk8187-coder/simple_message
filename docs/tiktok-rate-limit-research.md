# TikTok 冷会话限流（影子限流）研究记录

> 研究周期：2026-10-27 09:55 起  
> 数据来源：simple-message hub 生产环境（账号 jakson）真实群发 + 闭环探针测试  
> 状态：**进行中** —— 恢复时刻与内容因素的 A/B 实验由自动化探针执行中

---

## 1. 背景

2026-10-27 09:55 通过 hub 的群发队列（dispatch）向 55 个 TikTok 目标发送文本消息。  
任务参数：`batch_size=30`、`interval_s=5`（实际平均 16.1 秒/条，含发送与回读验证），  
发送账号 jakson，内容为统一文本 "hello"。

实测结果：**前 30 条全部成功送达，第 31 条起连续 6 条（#31–#36）被服务端静默丢弃**，  
10:05:56 手动暂停任务，剩余 19 条待发。

## 2. 现象：影子限流（Shadow Limit）

> **修正（10-27 15:12）**：初版"无任何客户端可感知信号"不准确——官方客户端
> 会有"等待后重试"的小字提示（用户实测）。但**网页协议通道的发送响应确实
> 不携带该信号**（见下），提示的数据源在官方客户端的其他链路，待定位。

被限流后的发送在我们的通道上表现为：

- WS ACK：`biz_code=0, "OK"`，正常回执，**且无任何附加帧**（深挖捕获 _others=0）
- HTTP `/v1/message/send`：HTTP 200，响应 body 即标准回执（cmd=100, biz=0,
  'OK'，消息被赋 msg_id 回显）——服务端**假装接收成功**，随后静默吞掉
- 回读验证：消息永远不出现在会话里（唯一可靠的判据）
- 金丝雀：无 ratelimit/auth 记录（API 层零错误码）

"等待重试"提示在官方客户端可见而我们的通道不可见，说明信号存在于
官方客户端使用的其他端点或长连接推送——已列为待定位项（见第 9 节）。

本次限流与常规 API 限流有本质区别：

| 维度          | 常规限流           | 本次实测                                           |
| ----------- | -------------- | ---------------------------------------------- |
| HTTP 状态/业务码 | 429 / 错误码      | **完全正常**（biz_code=0，guard_result="0"，tier="B"） |
| WS ACK      | 拒绝或报错          | **照常 ACK**（ack_kind="ack"）                     |
| 金丝雀采样       | ratelimit 类别告警 | **零痕迹**（仅无关的网络超时）                              |
| 消息实际去向      | 客户端可知          | **服务端收下后静默丢弃**，对方永远收不到                         |

判定依赖 hub 的**回读验证机制**（发送 → ACK → 轮询会话历史确认  
client_message_id 落地，12.5 秒窗口 × 5 次 → HTTP 通道兜底重发 → 再验证）。  
两通道均未落地即判定 dropped。**没有回读验证的话，本次群发会呈现  
"55 条全部发送成功"的假象，实际送达率 55%**。

## 3. 限流定位：三组闭环测试

全部测试在自有账号间完成（jakson / obb815 / 用户主号），未扰动外部用户：

| 测试 | 发送方 → 接收方       | 会话类型      | 结果                 |
| -- | --------------- | --------- | ------------------ |
| A  | jakson → 用户主号   | 热会话（已有互动） | ✅ 正常落地             |
| C  | jakson → obb815 | 冷会话（新建联）  | ❌ WS + HTTP 双通道均被吞 |
| B  | obb815 → jakson | 冷会话（新建联）  | ✅ 正常落地             |

### 结论

1. **账号级**：jakson 被限，obb815 完全正常——两者同 IP、同设备、同代理出口，  
   排除 IP/设备/网络因素
2. **维度是冷会话**：jakson 的热会话（已有互动的对话）发送完全正常，  
   被限的是**向陌生人/新对端发起的会话**（cold-start DM）
3. **触发阈值**：约 **30 条冷会话**——#1–30 全部落地、#31 起整齐地全部被吞，  
   截止线非常干净。时间窗 8.1 分钟（16 秒/条）
4. **形式为服务端配额计数器**：按账号在服务端维护，客户端无法读取/修改/绕过

## 4. 阈值模型（待实验区分）

两种候选模型，现有数据无法区分：

- **模型一：滑动窗口** —— "每 X 小时最多 30 条冷会话"，滚动恢复
- **模型二：日配额** —— "每自然日/每 24 小时 30 条"，定时重置

A/B 探测的阶梯频率设计即为此服务（见 §6）。

## 5. 内容因素假说

触发时全部消息为同一短文本 "hello"。内容是否参与限流判定（纯计数 vs  
计数+内容加权）未知。通过 A/B 探针实验验证（§6）。

## 6. A/B 探针实验设计（进行中）

### 6.1 设计

每轮在**同一时刻**发送两条冷会话探针，唯一变量是文案：

| 探针   | 文案                                   | 代表         |
| ---- | ------------------------------------ | ---------- |
| A（短） | `Hi! Quick hello from our team 👋`   | 原触发条件（短文本） |
| B（长） | 通用赞助邀约（夸赞 → 品牌介绍 → 付费合作形式 → 低门槛 CTA） | 真实业务场景     |

目标从原群发队列的待发条目中顺序消耗（每轮 2 条），探针后立即将对应  
队列项标记为已消耗，避免日后 resume 重复发送。

### 6.2 判定矩阵

| 短 A | 长 B | 结论                          |
| --- | --- | --------------------------- |
| ❌   | ❌   | 配额未恢复，继续下一轮                 |
| ✅   | ❌   | **内容是限流维持因素**——短文可过、营销结构被针对 |
| ✅   | ✅   | **纯计数型限流**——与内容无关，恢复即全量可发   |

### 6.3 频率策略（阶梯降频，弹药保护）

| 阶段           | 间隔        | 覆盖                    |
| ------------ | --------- | --------------------- |
| 前 4 轮（8 条探针） | 30 分钟     | 触发后 0–2.5 小时（高概率恢复窗口） |
| 4 轮未恢复       | 自动降为 2 小时 | 之后约 22 小时，覆盖 24h 假设窗口 |

预算：队列剩余 19 条 ÷ 2 条/轮 ≈ 9 轮，阶梯设计保证 26 小时内均有探测点。  
探测自动化（tiktok-rate-limit-probe）具备自动降频与自动停止能力，  
恢复时刻确定后自动退出并在本文件与 rate-limit-probe.log 留档。

**实验结论（10-27 14:44）**：

1. **商业话术在干净账号上不被针对**：6/6 全落地——内容因素在"触发"维度上
   排除（至少 13 条量级）；jakson 的限流是**计数型**（~30 条冷会话阈值）
2. **新号配额 ≥13 条/5 分钟**：obb815 未触发任何限流——新号冷启动配额与
   老号同量级（≥13），"新号天然低配额"假说部分排除
3. **未决**：30 条阈值是滑动窗口还是日配额仍未区分（需 jakson 恢复时刻
   数据）；商业话术在**更高量级**（30+）是否改变触发阈值未测

## 7. 运营策略结论

1. **冷会话配额是硬约束**：单账号高频冷启动必然触发影子限流，  
   且无任何客户端可感知的信号
2. **多账号轮换是第一解法**：obb815 同环境完全正常——55 目标拆分至  
   多账号（每号 ≤25 条/轮）可全部落在配额内
3. **回读验证必须常开**：影子限流下不验证等于盲发
4. **热会话不受限**：先互动后私聊的路径不受配额约束——  
   评论区互动 → 对方回复 → 热会话，是绕开冷配额的正路
5. **内容建议**：首条短、轻营销，合作细节放对方回复后的第二条  
   （两段式）；同文本大量重复本身是额外风控信号，正式投放应做  
   item 级文案变体
